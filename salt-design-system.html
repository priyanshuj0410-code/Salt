Salt Design System

v0.1

The design foundation for Salt. A modern ERP for Indian medical retail. This document defines the tokens, primitives, and patterns that every screen in Salt is built from. If a screen breaks one of these rules, the screen is wrong, not the rule.

Read top-to-bottom on your first pass. Reference by section after that. Code snippets are copy-pasteable Tailwind + CSS-variable patterns that work directly with shadcn/ui.

Principles

The six rules every design decision in Salt is checked against. When in conflict, earlier rules win.

1. Speed before delight

Salt is operated by cashiers on 12-hour shifts. Animation, illustration, and ornament cost cognitive cycles and create reaction-time penalties. We invest visual budget in information density and clarity of state, not in motion or decoration.

2. Keyboard is the primary input

Every action reachable by mouse must also be reachable by keyboard with a visible shortcut hint. Focus states are not an afterthought. They are how power users see what they're doing.

3. Trust through precision

This is financial software in a regulated category. Numbers align to the right with tabular figures. States are explicit (saved / saving / failed, never ambiguous). Audit cues are visible, not hidden.

4. Quiet by default, loud only when needed

Default surfaces are near-white. Color is reserved for state (red = danger, amber = warning, emerald = success). Decoration is forbidden. If everything is highlighted, nothing is.

5. Two densities, one system

Counter mode is compact (cashier needs to see 20 line items without scrolling). Owner mode is default density (reading reports without eyestrain). Both modes use the same tokens and the same primitives: only spacing and row height change. Never two design languages.

6. Indian-first, never Indian-only

Indian Rupees in en-IN formatting (₹1,00,000 not ₹100,000). Hindi/English bilingual where it matters. But avoid heavy cultural ornamentation. The customer doesn't want a "desi" product, they want a serious product that respects them.

Voice

  • Direct. "Bill saved" not "Your bill has been saved successfully."
  • Operational. "Pay & Print" not "Complete transaction"
  • Calm. No marketing exclamation marks. No emojis in product UI.
  • Bilingual where it matters. "Crocin 500" / "हिंदी" coexist; we don't translate "Pay" to "भुगतान करें" because cashiers prefer the short English form.

Semantic: for state, not decoration

Each semantic color has a foreground (text on white), a background tint, and a border. Use only for the meaning, never to differentiate categories.

Success
Saved, paid, in stock, on track
Warning
Near expiry, low stock, credit due
Danger
Out of stock, expired, overdue
Info
Sparingly. Hints, syncing, neutral notices
Rule. Never use semantic colors to differentiate categories or types. Salesperson A is not "green" and salesperson B "blue." Categories use shape, position, or label.

On-light vs on-dark semantic shades

The semantic foreground tokens (e.g. --color-warning = #b45309) are tuned to be readable as text on a white background, so they are deliberately dark. They must not be used as fills on dark surfaces or as whole-panel backgrounds. A dark amber fill reads as muddy rust, not warning. On dark surfaces (toasts, the inverse stat card), use the lighter -400 shades:

success on-dark #4ade80
warning on-dark #fbbf24
danger on-dark #f87171
The original bug. v0.1 filled a warning toast with --color-warning as the background. Because that token is a dark on-light foreground value, the toast rendered as a broken-looking brown panel. Fix: all toasts share the dark surface; semantic meaning comes from the dot + a 3px left border using the on-dark -400 shades.

Indian Rupee formatting

Always use en-IN locale: ₹1,00,000 (one lakh), ₹10,00,000 (ten lakh), ₹1,00,00,000 (one crore). The Indian grouping (2-2-3) is non-negotiable. Formatting Rs as 100,000 looks foreign and breaks trust. 

const formatINR = (n) => new Intl.NumberFormat('en-IN', {
  style: 'currency',
  currency: 'INR',
  maximumFractionDigits: 2,
}).format(n);

formatINR(1248750)  // → ₹12,48,750.00
formatINR(487.25)   // → ₹487.25

Spacing

Eight steps, 4px base. Use the smaller steps (1-3) inside compact components; the larger steps (4-8) for between sections. Never invent values.

Where to use what

  • space-1: icon to text inside a button, dot-to-label
  • space-2: between adjacent badges, within a kbd cluster
  • space-3: input internal padding (vertical), card divider padding
  • space-4: between form rows, card body small padding
  • space-5: card body default padding (owner mode)
  • space-6: page section spacing, header padding
  • space-8: between unrelated sections
  • space-12: page-level top/bottom whitespace, empty-state padding

Motion

Motion is functional, not decorative. Four durations, two easings. Always honor prefers-reduced-motion. Never animate in a way that delays the cashier seeing the result of their action.

instant 50ms Opacity-only micro-changes
fast 120ms Hover, focus, button press
medium 200ms Dropdown open, slide-in
slow 320ms Modal enter, full-screen transitions
Hard rule. Save & Print never animates exit. The bill must clear instantly so the cashier can start the next sale. Animation here is a productivity tax measured in real money.

Buttons

Three variants × three sizes. Use sparingly: a screen with five primary buttons has no primary action. Only one primary per surface for the main action.

Rule. Buttons never have icons larger than 14px. Icons sit at the left of the label for actions ("add", "save"), right of the label for navigation ("next", "view all").

Inputs

Two heights mapping to the density modes. Single focus treatment everywhere.

<input class="input" placeholder="..." /> (default · 36px) <input class="input input-compact" placeholder="..." /> (counter · 32px)

Focus state

The border is control (#898992, 3:1 or more) and darkens to action-primary; a solid 2px outline in focus-ring sits 2px outside it. No glow, no animation other than 120ms color crossfade. The outline shows on keyboard focus (:focus-visible) only.

Inline editable values (table cells)

For inline-edit fields inside tables (qty, discount %, batch picker), use a transparent input with a bottom border that darkens on focus. No box. Saves horizontal space.

Kbd hints

Salt is keyboard-first. Every shortcut is visible inline, not hidden in a tooltip or "help" panel. Kbd elements are 20px tall, slightly recessed (bottom border), monospace.

Open command palette ⌘K Park bill ⌃P Save & Print F12 Navigate ↑↓ Confirm ↵
Rule. Every interactive element with a shortcut shows the kbd hint inline at all times. Hidden shortcuts are technical debt, staff never discover them and complain the app is "slow."

Toasts & feedback

Inline feedback wins for primary actions (a checkmark next to the line item, "Saved" appearing next to the input). Toasts are for background events the user didn't initiate or isn't watching.

All toasts share one dark surface. The semantic meaning is carried by the status dot and a thin left accent border. Never by flooding the whole background with a semantic color. Flooding the background produces muddy, broken-looking panels (a dark amber fill reads as rust, not warning) and breaks visual consistency between toast types.

Accessibility

All checks must pass before any screen ships.

  • Contrast. Body text on white meets WCAG AA (4.5:1). Tertiary text only on white, never on surface-2.
  • Focus. Every interactive element shows the focus ring on :focus-visible. Never override browser focus without replacing.
  • Keyboard. Tab order matches visual order. No keyboard traps. Esc closes any overlay.
  • Semantic HTML. Tables are tables, buttons are buttons, headings are sequential.
  • Color independence. Status is never communicated by color alone. Always paired with text or icon.
  • Reduced motion. Honor prefers-reduced-motion: replace transforms with opacity, kill the pulse.
  • Zoom. All surfaces tested at 100/125/150% browser zoom, counter PCs are often zoomed.

Anti-patterns

Things you'll be tempted to do. Don't.

✕ Color-coded counter staff
Avatars in red/blue/green to identify cashiers. Use initials and zinc shades instead, color is reserved for state.
✕ Decorative icons in stat cards
A money bag next to "₹48,230" adds nothing. The number is the icon.
✕ Animated celebrations on bill save
The cashier bills 200x/day. A confetti burst is a productivity tax.
✕ Tooltip-only keyboard shortcuts
If a shortcut isn't discoverable inline, it doesn't exist. Show the kbd.
✕ Modal-on-modal flows
A batch picker inside a payment dialog inside a bill is too deep. Inline-expand on the main canvas.
✕ Toast for primary action confirmation
"Item added to bill" as a toast that disappears in 3s. The cashier already moved on. Use inline feedback next to the row.
✕ Decorative dividers
Horizontal rules with shadows, gradients, or ornaments. Use a 1px color-border line. Stop there.
✕ Inventing a new component
If you need a "card with a chart inside": that's Card with a chart inside. Don't make a ChartCard primitive.
